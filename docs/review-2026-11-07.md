### R-ISL-1: Low-battery warnings were lost in the move to Strand (UX-3a has regressed)

- [ ] **high** · bug · effort S · verifier: **confirmed**
- **Status: skipped.** By decision: "Low battery warnings are fine."
- Where: `dot_config/strand/island.strand:63-64, 509-513, 595-600`

**Evidence.** docs/ux-backlog.md UX-3a (Quickshell): "notify-send ... at 15% and critical at 5% while discharging, one per threshold per discharge cycle". In Strand the only warning is the tint of the 16 px glyph: `battery_color()` returns warn below `battery_low = 0.2` and danger below `battery_out = 0.1`. No file in dot_config/strand sends a notification about the battery (grep 'battery' finds only island.strand and launcher.strand). /etc/UPower/UPower.conf has PercentageAction=2.0 and CriticalPowerAction=Auto, and hypridle.conf says auto-suspend was removed because of the xe crash.

**Suggestion.** Bring back the latched warnings. Add `permit exec "notify-send"` and an action such as `alert(urg: text, msg: text) ["notify-send", "-u", urg, "-a", "Battery", msg]`. Then `on change battery.percent` while `!battery.charging`: send a normal warning once below battery_low and a critical one below battery_out, using `state` latches that reset only when the battery climbs back above the threshold. Do not reset on AC state, so a flapping charger does not repeat them, as UX-3a did. The warning then reaches every monitor and is kept in the history, instead of being an orange pixel on a laptop that may be docked with the lid shut.

**Verifier.** Correct, and a regression. ux-backlog.md:51 marks UX-3a done for Quickshell (15% warning, 5% critical, latched, reset only when the charge recovers above the threshold, not on AC). In the live config, grep finds 'battery' only in island.strand and launcher.strand, and only theme-switch, screenshot, win-vm and hyprland.lua.tmpl send notify-send. No strand file has `permit exec "notify-send"` (launcher has qalc/sh/theme-switch, record has mkdir/wf-recorder). Strand's notifications service has no way to post a notification itself, so notify-send is the right route (libnotify 0.8.9 is installed). UPower.conf confirms PercentageAction=2 with CriticalPowerAction=Auto, so the only backstop is a forced hibernate or poweroff at 2%. The suggested latch design matches UX-3a. One addition: check once after `armed` as well as on change, so starting already below a threshold still warns, the bug UX-3a's own review caught. High is fair even though the laptop is mostly docked.

### R-ISL-2: A faillock lockout shows as "Wrong password" on the lock, so the correct password looks wrong for 10 minutes

- [ ] **medium** · bug · effort S · verifier: **confirmed**
- **Status: partial.** (1) done in 9c0dfc3: the lock shows PAM's own message ahead of "Wrong password". (2) /etc/pam.d/strand is not written: it's a system file for you to run with sudo, and it should be tried in the lock VM first (the verifier warns that `requisite` can loop).
- Where: `dot_config/strand/lock.strand:5-6, 61, 149-150; /etc/pam.d/system-auth:3,8 (no /etc/pam.d/strand)`

**Evidence.** /etc/pam.d/strand is missing, so strand-auth uses `login` → system-auth. That stack has `auth required pam_faillock.so preauth` and `authfail`, and faillock.conf is all defaults (deny=3, unlock_time=600). With `required`, faillock's "account is locked" text is followed at once by the password prompt, and Strand clears `message` when a prompt arrives (crates/strand-services/src/auth.rs, the Prompt arm: `s.message.clear()`). The refusal then sets `wrong`, and lock.strand:149 puts `if wrong { "Wrong password" }` ahead of `auth.message`. The header also says "the key you pressed is already in the field", so a letter or Space pressed to wake the screen gets prepended to the password and counts as a failure. Three of those in 15 minutes lock the account for 10 minutes, and the lock says nothing more than "Wrong password". hyprlock goes through the same system-auth.

**Suggestion.** (1) In lock.strand, show `auth.message` ahead of the generic text: `if auth.message != "" { text auth.message } else if wrong { text "Wrong password" }`. (2) Write /etc/pam.d/strand (system file: plan it first, run it from another terminal, and try it in the lock VM). Start it with `auth requisite pam_faillock.so preauth`, then `auth include system-local-login` and `account include system-local-login`. With `requisite`, the conversation ends on the lockout text, which then stays visible. This also removes the one-time 'login fallback' warning on every start. (3) Optionally raise `deny` in /etc/security/faillock.conf, or don't let a wake key land in the field while the field is hidden at rest.

**Verifier.** The mechanism checks out. /etc/pam.d/strand is missing, so Strand uses login → system-local-login → system-login → system-auth, which has `auth required pam_faillock.so preauth`. faillock.conf is all defaults (deny=3, unlock_time=600). In crates/strand-services/src/auth.rs the Prompt arm runs `s.message.clear()`, so under `required` the 'account is locked' text is wiped as soon as pam_unix prompts, and the refusal sets `failed` → `wrong` → "Wrong password" (lock.strand:149). Fix (1) is needed as well as (2): the third real failure leaves `wrong` true, and it sits ahead of auth.message. Caveat on (2): auth.rs re-begins a conversation with a submitted password that PAM never consumed (`late` = take_back filtered by !answered → `next`). Under `requisite` a password typed during the lockout may restart conversations over and over until unlock_time passes. Run it in the lock VM, as suggested, before deploying. Medium, not high: a lockout takes 3 failures in 15 min. The wake key landing in the field (a deliberate design, lock.strand:110-111) makes that more likely, but it still happens only now and then.

### R-ISL-3: Critical and persistent notifications vanish: any newer notification bumps them, and they time out while locked

- [ ] **medium** · bug · effort S · verifier: **partly**
- **Status: skipped.** By decision: a newer notification replacing the current one is by design.
- Where: `dot_config/strand/notify.strand:46-50, 96-100, 107`

**Evidence.** `on notifications.received(n) { if !notifications.dnd || n.urgency == critical { for p in notifications.popups { if p.id != n.id { p.expire() } } } }` expires a critical popup the moment a normal one arrives, such as a Spotify track change. `life_of` never reads `n.persistent` (types.md: "The sender asked it never to expire ... `after n.timeout ?? 6s while !n.persistent`"), so an expire_timeout of 0 still goes after 5 s. features.md lists "Notifications that ask to stay still vanish after 5 s (U4)" under problems not to carry over, so this has regressed. `after life_of(n) while !c.hover` also keeps counting behind the lock, so a critical notification that arrives while locked has expired before you see it.

**Suggestion.** In `received`, skip critical popups: `if p.id != n.id && p.urgency != critical { p.expire() }`. Prefer one when choosing what to show: `current = ... notifications.popups.filter(p => p.urgency == critical).last ?? notifications.popups.last`. Pause the timer for persistent notifications and while locked: `after life_of(n) while !c.hover && !n.persistent && !lock.locked { n.expire() }` (lock.locked is already exported). Decide whether critical ones should also wait for a dismiss rather than 10 s; the freedesktop spec says they should.

**Verifier.** The code matches the description. `received` expires every other popup, critical ones included. `life_of` never reads `n.persistent`. `after life_of(n) while !c.hover` keeps counting while locked (spec 8.4: the count pauses only while the condition is false, and the Notify panel stays open under the lock). The persistent case is a regression against features.md's 'problems not to carry over' (U4). However, critical cards expiring was explicitly accepted in the Quickshell era (ux-backlog.md:20, 'accepted, the pulsing red bar icon is the persistent signal'). That signal is gone now (the bell is accent whatever the urgency), so the case is worth reopening rather than calling it a regression. Correction to the suggestion: what is drawn comes from `notifications.popups.reverse().take(...)` at notify.strand:89, not from `current`. Preferring a critical one means changing line 89 to the same choice (or rendering `current`), or the card and open_key/clear_key would disagree. The rest of the fix (skip critical popups in `received`; `while !c.hover && !n.persistent && !lock.locked`) is sound.

- [ ] **medium** · ux · effort S · verifier: **confirmed**

### R-ISL-5: The island's bell is always lit, because it counts history rather than unread notifications

- [ ] **low** · ux · effort S · verifier: **partly**
- **Status: skipped.** By decision: notification history already covers it, so the bell keeps its "not yet cleared" meaning.
- Where: `dot_config/strand/island.strand:473-479`

**Evidence.** `if notifications.dnd || notifications.count > 0 { Sym "notifications_unread" { tint: $accent } }`. services.md: `count` is "How many notifications are kept", up to 1,000, remembered across restarts, and expired popups stay in `all`. Nothing in island.strand or launcher.strand records what has been seen (no seen/unread state). A grim of the island on DP-2 shows the accent bell lit in normal use, so the bell carries no information and adds a permanent accent-coloured dot.

**Suggestion.** Keep a persisted marker of what has been seen (`state seen_at ... persist`, the newest notification's time or id). Set it when the Notifications page opens, or when a card is clicked or cleared. Light the bell in the accent only when `notifications.all.any(n => <newer than seen_at>)`. Otherwise hide it, apart from the DND glyph.

**Verifier.** The bell is not 'history instead of unread' by accident. features.md defines it as 'Until a notification is opened or cleared, the island shows a bell with a dot', an inbox model, and `count` is exactly what has not been dismissed (expire() keeps it in `all`). In practice it is always lit anyway: the persisted store holds 54 notifications going back to 2026-11-04, because timed-out popups are never dismissed and come back after restarts. So the defect is real, but it comes from the inbox model plus persistence, not from a miscount. A cheaper fix than a full seen-tracker: a persisted `seen_at` set when the Notifications page opens, with the bell lit only for `notifications.all.any(n => n.time > seen_at)`. Or keep the inbox meaning and accept that the bell means 'not cleared'. Low: it is a constant accent dot, not a malfunction.
